# 조직 단위 운영 절차

## 신규 고객·담당자 페이지

1. `/proposal`에서 실제 제공 범위를 설명합니다. 고객관리·자동 발송·온라인 가입 서비스로 설명하지 않습니다.
2. 조직의 표준 레이아웃·팔레트와 필요한 상담 목적을 정합니다. `/studio`에서 추천 원고를 선택합니다.
3. 담당자의 이름·소속·연락처·실제 취급 범위를 확인합니다. 타인의 데모 프로필을 납품 페이지에 남기지 않습니다.
4. 사진 사용권과 사실인 경력·등록정보만 반영합니다. 예시 후기나 가상의 실적을 만들지 않습니다.
5. 제작 JSON을 받아 기존 `studio:import` 절차로 초안을 생성합니다. 초안은 검색 비공개이고 자동 게시되지 않습니다.
6. 소속 조직이 원고와 표시 정보, 필요한 심의 여부를 확인합니다. 조직의 검토가 끝나지 않은 운영 페이지는 게시하지 않습니다.
7. 도메인·연락처·오픈채팅방 소유를 확인하고 320·360·390·768·1440px 검수 및 실제 스마트폰에서 링크를 점검합니다.
8. 명시적으로 승인된 버전만 Git의 검토·병합 절차로 공개합니다. 승인 범위와 변경 내용을 커밋/PR에 기록합니다.

## 역할과 계약에서 정할 것

제작비에 포함되는 페이지 수, 수정 횟수/범위, 원고 검토 주체, 도메인 소유자, 담당자 퇴사·소속 변경 시 처리, 연락처 변경 책임, 유지관리 범위를 별도로 정합니다. 현재 프로젝트에는 사용자 계정·역할별 권한·승인 대시보드·전자결재가 없습니다.

## 변경 작업

개별 정보는 해당 `sites/<id>/site.json`, 사진은 `public/sites/<id>/`에 반영합니다. 생성된 레지스트리는 `npm run generate`로 재생성합니다. 공통 렌더러 수정은 모든 페이지에 영향을 주므로 5개 배치×6개 팔레트 및 자유 편집의 회귀 테스트를 실행합니다.

새 원고·사진·연락처를 적용할 때 이전 승인 번호가 자동으로 유효하다고 간주하지 않습니다. 제작 JSON 저장/불러오기는 기존 심의번호와 상태를 초기화합니다. 운영 설정의 `pending`은 검증 오류입니다. `approved`와 `not-required`는 해당 조직이 확인한 판단을 기록하는 값입니다.

## 배포 확인

```bash
npm run check
npx playwright install chromium
npm run test:e2e
```

기존 CI를 변경하거나 실패 검사를 무시하지 않습니다. 병합 전 최신 main과 비교하고 기존 고객 변경을 보존합니다. 배포 후 `scripts/verify-live.mjs`는 연락 방식·버전·API 종료·편집기 경로를 검사합니다. 실제 통화와 채팅방 열림은 별도 사용자 기기 확인이 필요합니다.

## 정기 점검

연락처·소속·사진·도메인, 외부 채팅방의 접근 가능 여부, 게시 원고의 승인 범위와 필요 시 유효기간을 점검합니다. 문의 정보가 이 사이트의 수신함에 쌓이는 구조가 아니므로 담당자의 전화·오픈채팅 관리 책임을 명확히 합니다. 기기 내 초안은 서버 백업이 아니므로 제작 JSON과 Git 이력을 보관합니다.
