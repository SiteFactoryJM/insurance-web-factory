# 카카오톡 상담 연동 계획 — 현재는 실행하지 않음

작성 기준: 2026-09-08. 이 문서는 다음 개발 단계의 설계 메모이며 카카오톡 발송 구현, 운영 승인 또는 개인정보 동의 문안의 확정본이 아니다.

## 1. 현재 구현의 경계

신청 UI는 4단계 **브라우저 내 데모**다. 분야 선택, 선택적 상황 작성, 연락 정보 입력, 최종 확인, 안내 확인, 완료 화면만 작동한다. 실제 개인정보 대신 예시 정보를 사용해야 한다.

- fetch / XMLHttpRequest / sendBeacon / 메일 앱 / Kakao SDK를 호출하지 않는다.
- 서버·D1·Webhook·localStorage·sessionStorage·IndexedDB에 저장하지 않는다.
- URL 쿼리에 입력값을 넣지 않는다. 미리보기 테마 식별자만 URL에 사용한다.
- 최종 확인은 `textContent`로 구성해 HTML 삽입을 막는다. 연락처는 마스킹해서 보여준다.
- 완료, 재시작, 페이지 이탈 시 입력값과 확인 요약을 지운다. 뒤로가기 캐시 복원도 초기화한다.
- 자바스크립트가 없으면 입력 필드와 다음 버튼이 비활성화되어 전송되지 않는다.
- `/api/consultations`도 `demo.enabled`인 사이트에서는 본문 파싱 이전에 반환한다. 실수로 `submissionMode: store`를 설정해도 저장하지 않는다.
- 기존 비데모 저장 API는 레거시 코드로 남아 있지만 **새 신청 UI에는 연결되어 있지 않다**. 설정만 바꿔서 운영을 시작하면 안 된다.

## 2. 먼저 결정할 발송 목적

### A. 담당 설계사에게 신규 상담 알림

운영자가 가장 먼저 결정해야 할 흐름이다. 여러 설계사 중 누구에게 알릴지 서버가 검증된 사이트·도메인 정보에서 결정한다. 사용자 입력의 담당자 전화번호, 수신자 ID 또는 URL을 신뢰하지 않는다. 알림에는 접수번호와 최소한의 요약만 넣고 전체 개인정보는 인증된 관리 화면에서 확인하도록 설계한다.

### B. 신청 고객에게 접수 안내

고객의 접수 사실을 알리는 정보성 메시지가 필요하다면 카카오 비즈메시지/알림톡 사용 가능 여부와 공식 딜러사 연동을 검토한다. 발신 채널, 사업자 요건, 템플릿 승인, 수신번호 처리, 비용, 실패 시 대체 수단을 확정해야 한다. 광고 목적의 메시지는 접수 안내와 분리한다.

### C. 고객이 카카오톡 채팅창을 직접 여는 방식

카카오톡 채널 또는 오픈채팅 링크로 이동하는 것은 신청서 내용을 자동 발송하는 기능과 다르다. 현재 저장된 `contact.kakaoUrl`을 자동 발송 API 주소로 사용하면 안 된다. 개인정보를 채팅 URL에 넣어 넘기지도 않는다.

카카오 Developers의 메시지 API는 동일 서비스 사용자 간 발송, 사용자 동의와 권한 등의 제약이 있다. 일반적인 전화번호 기반 임의 발송이나 30~40명 설계사에게 무제한 전달하는 API로 가정하지 않는다. `나에게 보내기`를 곧바로 다수 설계사 운영 구조에 적용하지 않는다.

## 3. 제안하는 운영 구조

```text
상담 폼
  → 자사 Worker의 /api/consultations
  → 요청 크기 제한 · 입력/동의 검증 · 스팸/중복 방지
  → 도메인에서 siteId 및 승인된 담당자 해석
  → 최소 보유 접수 레코드 + 발송 작업(outbox)
  → 서버 측 발송 어댑터 / 큐
  → 계약된 비즈메시지 제공사
  → 발송 상태 콜백 검증 및 상태 기록
```

클라이언트에 API 키, 시크릿, 발신 키, 액세스 토큰, 수신자 매핑 테이블을 넣지 않는다. Worker secrets 또는 승인된 서버 측 비밀 관리 체계를 사용한다. 설계사별 수신 대상은 서버 전용 설정으로 관리하고 HTML에 포함하지 않는다.

`queued`, `sent`, `delivered`, `failed`를 구분한다. HTTP 200만으로 실제 전달 성공으로 판단하지 않는다. 제공사 오류 응답과 비즈니스 상태 코드를 확인하고, 콜백 서명·발신자 검증을 적용한다. 중복 접수·중복 발송 방지를 위한 멱등성 키, 제한된 재시도, 최종 실패 보관 및 담당자 확인 절차를 둔다.

현재 레거시 API의 Webhook 경로는 응답 상태와 부분 실패를 충분히 처리하는 완성된 발송 어댑터가 아니다. 현 상태의 `CONSULTATION_WEBHOOK_URL`에 카카오 주소만 넣어 활성화하지 않는다. 운영 전 요청 크기 제한, 서버 검증, 발송 응답 판정, 큐/재시도, 접근 제어, 저장·발송 실패 복구를 별도로 구현하고 테스트한다.

## 4. 요청 데이터 초안

```ts
// 서버 계약 초안. 현재 데모에서는 이 객체를 전송하지 않는다.
interface ConsultationRequest {
  topicId: string;             // 서버가 해당 사이트의 취급 가능 목록과 대조
  message?: string;            // 선택, 길이 제한; 민감정보 입력 금지 안내
  name?: string;               // 호칭 허용, 실제 필요성 검토
  phone: string;
  contactMethod: 'phone' | 'sms' | 'kakao';
  contactTime?: string;        // 예약 확정 시각이 아닌 희망 시간
  privacyNoticeVersion: string;
  privacyConsent?: boolean;   // 법적 처리 근거와 실제 동의 필요성 확정 후 결정
  idempotencyKey: string;
}
```

`siteId`와 `agentId`를 요청 본문만으로 확정하지 않는다. 기존 클라이언트 데이터의 한국어 표시값은 운영 시 안정적인 ID와 분리한다. 마케팅 동의는 필요한 경우에만 별도 선택 항목으로 두고 미리 체크하지 않는다. 카카오톡 연락 방법을 선택했다고 마케팅 수신에 동의한 것으로 해석하지 않는다.

## 5. 실제 운영 전 체크

실제 취급 상담 분야, 무료 상담 조건, 담당자 수신 경로, 영업 시간, 개인정보 처리 주체, 위탁/제3자 제공 구분, 보유기간과 삭제 절차, 동의 문안, 광고심의 및 소속 조직 승인을 확정한다. 생년월일·주민번호·병력·증권 업로드는 현재 접수 폼에 추가하지 않는다.

로그에는 전체 연락처나 자유 입력 원문을 남기지 않는다. 장애 추적은 비식별 접수 ID를 사용한다. 운영/시험 채널과 수신번호를 분리하고 테스트 데이터만으로 검증한다. 실제 고객 발송은 별도 승인 뒤 활성화한다.

## 6. 연결 지점

`src/render/shared.ts`의 신청 필드와 안내 문구, `src/render/client-script.ts`의 최종 제출 처리, `src/routes/consultation.ts`의 서버 계약이 연동 대상이다. 데모와 운영 어댑터를 분리하고 `demo.enabled`의 미전송 방어는 삭제하지 않는다. `sites/<id>/site.json`의 `consultation.topics`로 취급 분야를 제한한다. 새 어댑터 활성화 후에도 현재 미전송 테스트를 데모 전용 회귀 테스트로 유지한다.
