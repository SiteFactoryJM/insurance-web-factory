# 2026 디자인 레퍼런스와 콘텐츠 개편 기준

조사일: 2026-09-08. 대상: 보험설계사 소개 사이트, 디자인 샘플 선택 도구, 상담 신청 데모와 설계사 자료수집 설문.

이 문서는 **공식 페이지에서 확인한 내용**, **사용자 제공 화면에서 관찰한 문제**, **이 프로젝트에 적용할 설계 판단**을 구분한다. 트렌드 글은 디자인 기업의 편집 의견이며 한국 보험 상담의 전환율을 입증한 연구가 아니다. 글자수 기준도 이 프로젝트의 편집 규칙이다.

## 조사 방법과 범위

웹 검색으로 2026년 트렌드 글을 찾고 금융·보험·법률·프리미엄 서비스의 공식 홈페이지와 디자인 시스템 문서를 직접 열어 콘텐츠·CTA·정보 구조를 확인했다. 연결형 브라우저가 없어 프로젝트에 설치된 Playwright/Chromium으로 별도 읽기 전용 세션을 열어 공식 사이트 4곳을 1440×1000px로 캡처하고 이미지를 직접 확인했다. 각 페이지는 HTTP 200으로 열렸고 로그인·양식 전송은 하지 않았다. Aman은 쿠키 안내와 미디어 재생 오류가 발생해 헤더·색상·텍스트 위계만 관찰했다.

아래 실측값은 캡처 시점의 CSS 계산값이며 서체명은 선언된 폰트 스택이다. 사용자 환경에서 실제 선택되는 대체 서체, 동적 영상·애니메이션, 모바일 레이아웃까지 동일하다는 뜻은 아니다. 영문 사이트의 글자 크기를 한글 보험 사이트에 그대로 적용하지 않는다.

사용자 제공 화면에서는 후기 영역과 FAQ 영역의 배경이 연속되고, 후기의 긴 문장과 넓은 공백이 반복되어 새 섹션의 시작을 빠르게 구분하기 어렵다. 후기는 실제 고객 후기가 아닌 예시임을 밝히고 있으므로 개편 후에도 이 표시는 유지한다.

## 화면·문구 개편 판단

1. **샘플 도구를 페이지 최상단에 배치한다.** 배치·팔레트 선택과 전체 비교는 실제 사이트 헤더 밖의 별도 띠에 둔다. 도구 이름과 미리보기 경계를 밝힌다. 운영 페이지의 탐색 메뉴처럼 보이지 않게 한다.
2. **사이트 헤더의 읽는 순서를 정돈한다.** 왼쪽은 전체 이름·직함·소속, 오른쪽은 탐색과 주 CTA로 구성한다. 의미가 불분명한 성씨 한 글자 마크는 제거한다. 좁은 화면에서는 메뉴와 상담 행동의 공간을 확보한다.
3. **색만 바꾸지 않고 섹션 경계도 만든다.** 소개·상담 분야·진행 과정·후기·FAQ 사이에 밝은 면, 옅은 색면, 진한 강조면의 리듬을 준다. 면 전환에 상하 여백·상단선·제목 위치를 함께 사용한다. 카드 내부 문장은 배경과 독립된 가독성 높은 면에 둔다.
4. **짧은 문구에도 구체적인 의미를 남긴다.** “맞춤 솔루션을 제공합니다” 같은 포괄적 표현보다 “가입 내용을 함께 확인합니다”, “유지할 예산을 먼저 정합니다”처럼 상담에서 하는 일을 설명한다. 근거 없는 절감·성과·최고 표현은 추가하지 않는다.
5. **휴대폰에서 같은 정보를 짧게 전달한다.** 첫 화면 문구, 소개, 카드 설명, FAQ 답변에 모바일 문구를 따로 받는다. 소개를 줄이더라도 이름·소속·상담 범위·연락 경로는 유지한다. 보험 고지·개인정보·동의·예시 후기 표시는 문구 축약 대상에서 제외한다.

## PC·모바일 문구 작성 기준

공백과 문장부호를 포함한 Unicode code point 기준이다. 아래 값은 이 사이트의 레이아웃과 읽기 부담을 고려한 **프로젝트 편집 상한**이며, 보편적인 UX 연구 수치가 아니다. 긴 문장은 자동으로 자르지 않고 편집 단계에서 수정한다. 모바일 문구가 없으면 기존 PC 원문을 사용하므로 모바일 미리보기 확인이 필요하다.

| 입력 항목 | PC 상한 | 모바일 상한 | 작성 방향 |
| --- | ---: | ---: | --- |
| 첫 화면 제목 | 40자 | 24자 | 누구에게 어떤 도움을 주는지 한 가지 메시지 |
| 첫 화면 설명 | 120자 | 60자 | 상담에서 확인할 내용 한두 문장 |
| 소개 제목 | 40자 | 24자 | 상담 원칙 한 가지 |
| 소개 본문 | 400자 | 100자 | PC는 원칙과 방법, 모바일은 핵심 방법 중심 |
| 콘텐츠 카드 설명 | 120자 | 48자 | 카드 하나에 한 가지 도움 또는 확인 항목 |
| FAQ 답변 | 240자 | 80자 | 결론부터, 필요한 조건과 주의사항은 유지 |

예: PC 제목 “지금 가입한 보험, 필요한 보장부터 함께 확인합니다.” → 모바일 제목 “내 보험, 필요한 보장부터”. 문장을 두 버전으로 관리해도 의미와 실제 취급 범위는 동일해야 한다. 자료수집 설문에는 `PC 문구`, `모바일 문구`, 각각의 글자수 상한과 예시를 함께 표시한다.

## 상담 설문과 자료수집 설문

상담 신청 데모와 설계사 자료수집은 목적이 다르므로 질문도 구분한다.

| 대상 | 질문 구성 | 이유와 출처 |
| --- | --- | --- |
| 방문자 상담 신청 | 먼저 상담 분야를 묻고, 필요한 경우 선택형 상황 또는 선택 메모를 받는다. 연락 정보와 최종 확인은 뒤에 둔다. | [GOV.UK 질문 페이지](https://design-system.service.gov.uk/patterns/question-pages/)는 각 질문의 필요성을 확인하고, 선택 항목과 모름 응답을 명확히 하며, 한 번에 하나의 질문에 집중하도록 권장한다. |
| 다단계 신청 | 현재 단계/전체 단계, 이전 단계, 선택 단계 건너뛰기, 최종 요약을 제공한다. 데모의 전송·저장 없음은 시작과 최종 확인에서 짧고 명확하게 설명한다. | [W3C WAI 다단계 양식](https://www.w3.org/WAI/tutorials/forms/multi-page/)은 논리적으로 묶인 단계, 진행 안내, 선택 단계의 식별과 건너뛰기를 설명한다. |
| 설계사 자료수집 | 방문자 대상·상담 분야·상담 원칙·확인 가능한 경력·선호 CTA를 묻고, 화면에 실을 문구는 PC/모바일 두 칸으로 받는다. 선택한 디자인 배치와 팔레트도 구분한다. | 위 질문 설계 원칙을 자료수집 목적에 적용한 프로젝트 판단이다. 막연한 장문 자기소개 대신 실제 화면에 필요한 답을 받는다. |
| 길이 안내 | 입력 전에 상한을 보여주고 초과한 항목을 명확하게 알려준다. 기기별 문구 제한과 고객의 자유 메모 제한을 같은 것으로 취급하지 않는다. | [GOV.UK 글자수 컴포넌트](https://design-system.service.gov.uk/components/character-count/)는 제한할 이유가 있을 때 카운트를 쓰고 지나치게 좁은 제한을 피하도록 설명한다. |

상담 데모에 실제 보험증권·주민등록번호·진단명 입력을 유도하지 않는다. 예시 정보로 동작을 확인하며, 현재의 서버 미전송·브라우저 저장소 미사용 원칙을 유지한다. 자료수집에서 후기를 받는 경우에도 실제 고객의 동의와 공개 가능 여부를 확인하고 예시를 실제 후기로 바꾸지 않는다.

## 검증할 결과

- 320·360·390·768·1440px에서 헤더의 정렬, 섹션 경계, 문장 줄바꿈을 확인한다.
- 모바일 전용 문구가 실제 표시되고 PC 문구와 중복해서 읽히지 않는지 확인한다.
- 글씨를 작게 줄이거나 말줄임표로 숨기지 않고, 200% 글자 확대에서도 읽고 조작할 수 있는지 확인한다.
- 최하단 CTA가 본문·FAQ·양식·푸터를 가리지 않는지 확인한다.
- 입력 필드의 라벨·선택 항목·오류·단계 이동과 데모 미저장을 확인한다.
- 디자인 결과 검증과 상담 전환 개선 입증은 구분한다. 전환율 개선은 이번 자료 조사만으로 단정하지 않는다.
